# klix v0.4.0 / v0.5.0 — Fünf Feature-Wellen (Implementation Plan)

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Fünf geplante Features in zwei Releases umsetzen: Regel-Engine im Head, automatische Threshold-Kalibrierung, `explain()`, `validate_anchors()` und Batch-Inference — alle opt-in, rückwärtskompatibel, CPU-schnell.

**Architecture:** Alles baut auf dem vorhandenen Shared-Backbone-Design auf. Keine neuen Abhängigkeiten (nur numpy/scipy/sklearn, die schon da sind). Kein Rust in 0.4.x — der Profiling-Befund (Embedding-Pass ~10 ms dominiert, Kopf-Mathe < 1 ms) macht Rust/Threads vorerst zu falscher Optimierung; stattdessen echte Batch-Vektorisierung.

**Tech Stack:** Python 3.10+, numpy, scipy.sparse, scikit-learn (LogisticRegression), fastembed. Release-Kette: version bump → tag → GitHub Actions publish.

Rust bleibt als optionales Zukunfts-Wheel notiert.

## Feature 3: Regeln im Choice-Head (`rules` / StrictChoice-Verhalten)

**Objective:** Harte Keyword-/Regex-Regeln, die semantische Ergebnisse überschreiben oder boosten — deklarativ, in einem Kopf.

**API:**

```python
from klix import Rule, RuleMode  # neu

engine.add_head(Choice(
    name="route",
    options={...},
    rules=[
        Rule(label="ot_plant", any_of=["notfall", "stillstand"], mode="force"),
        Rule(label="security", pattern=r"\b(?:10\.\d+\.\d+\.\d+|root@)\b", mode="boost", weight=2.0),
    ],
))
```

**Files:**
- Create: `src/klix/rules.py` (Rule dataclass, RuleMode enum, Kompilierung zu Regex)
- Modify: `src/klix/heads.py` — `Choice.__init__(rules=None)`, `Choice.fit()` kompiliert Regexes, `Choice.evaluate()` wendet Regeln an (BOTH paths: nearest UND linear-probe, Regeln gewinnen immer)
- Test: `tests/test_rules.py`

**Details evaluate-Integration (beide Pfade):**
1. Nach der Label-Entscheidung: für jede Rule prüfen `rule.compiled.search(encoded.text)`
2. `mode="force"`: match → `value=label`, `details["forced_by"]=rule Beschreibung`, skip normal logic
3. `mode="boost"`: `category_scores[label] += weight` vor der Max-Wahl
4. `details["matched_rules"]`: Liste der getretenen Rules (für Explain + Debug)

### Task 3.1: Rule dataclass + Regex-Kompilierung
- Create `src/klix/rules.py`: `@dataclass Rule { label: str, any_of: list[str], mode: str = "boost", weight: float = 2.0 }`
- Funktion `_compile_rules(rules) -> list[(compiled_regex, Rule)]` — Wortgrenzen-Regex aus Keywords bauen, Sonderzeichen escapen
- Test: `tests/test_rules.py::test_rule_compiles_to_regex`
- Run: `uv run pytest tests/test_rules.py -v` → PASS

### Task 3.2: Choice akzeptiert `rules` und wendet sie im nearest-Pfad an
- Modify `src/klix/heads.py`: `__init__(rules=None)`, `self._compiled_rules = []`; in `fit()` kompilieren
- In `evaluate()` (nearest-Pfad): force-Rules zuerst prüfen; boost-Rules auf category_scores addieren
- Test: `test_force_rule_overrides_semantics`, `test_boost_rule_tips_close_call`, `test_matched_rules_in_details`
- Run: pytest → PASS

### Task 3.3: Regeln im linear-probe-Pfad
- Probe liefert Wahrscheinlichkeiten; force-Rules überschreiben danach (`value=label, score=1.0, forced=True`), boost-Rules addieren `weight` auf die Probability des Labels (clipped 0..1)
- Test: linear + force rule → erzwungenes Label trotz gegenteiliger Semantik
- Run: pytest → PASS, commit

## Feature 2: `calibrate()` — automatische Schwellenwerte

**API:**

```python
report = engine.calibrate("is_security", samples=[("text", True), ("text", False), ...])
# -> {"threshold": 0.42, "metric": "f1", "value": 0.91, "n": 12}
# setzt head.threshold dauerhaft

engine.calibrate("route", samples=[("text", "billing"), ("text", None), ...])
# kalibriert reject_threshold (None-Labels = "weiß nicht nicht")

engine.calibrate("urgency", samples=[("text", 2.5), ...])
# grid-search sharpness + lineare Remap (a,b) via kleinste Quadrate
```

**Files:**
- Modify: `src/klix/heads.py` — `Flag.calibrate(samples, metric="f1")`, `Choice.calibrate(samples, metric="accuracy")` (nur reject_threshold), `Score.calibrate(samples)`
- Modify: `src/klix/engine.py` — `DecisionEngine.calibrate(head_name, samples, metric="f1")` → delegiert, gibt Report zurück
- Test: `tests/test_calibrate.py`

**Implementierungsdetails:**
- Flag: Wahrscheinlichkeiten für alle Samples einmal berechnen, Kandidaten = sortierte unique probs + 0.5, für jeden Kandidaten F1/Precision/Recall/Accuracy berechnen, bester gewinnt. `self.threshold = best`. Warnung wenn `len(samples) < 8` (F1-Schätzung rau).
- Score: grid over sharpness ∈ [2..16 step 1], je Sharpness Sigmoid-Werte berechnen, lineare Regression `target ≈ a + b·value`, SSE; bestes (sharpness, a, b) — `a`/`b` als neue Optionale `calib_a`, `calib_b` in `evaluate()` anwenden. (Kein scipy.optimize nötig.)
- Report enthält `n`, Warnung bei wenigen Samples.

### Task 2.1: Flag.calibrate (TDD)
- Failing test: 10 synthetischer Samples mit klarem Trennschnitt bei ~0.4 → nach calibrate ist `threshold` ≠ 0.5 und F1 > 0.9
- Implementieren (Sweep ~15 Zeilen), Test PASS
### Task 2.2: Choice.calibrate (reject_threshold)
### Task 2.3: Score.calibrate (sharpness grid + affine Remap)

## Feature 5: `res.explain()` — Explainability

**API:**

```python
res = engine.decide("plc-34 meldet fehler, förderband steht sofort")
print(res.explain("route"))
# {
#   "value": "ot_plant",
#   "because": [
#     {"kind": "keyword", "token": "plc-34", "weight": 0.98,
#      "anchor": "plc-34 fehler"},
#     {"kind": "semantic", "anchor": "robot cell stopped", "similarity": 0.72},
#   ],
#   "runner_up": {"label": "it_ops", "score": 0.41},
#   "rejected": False,
# }
```

**Files:**
- Modify: `src/klix/heads.py` — `Choice.explain(encoded) -> dict` (nearest + linear Pfad); `Score.explain`, `Flag.explain` (kürzer: Pole-Similarities)
- Modify: `src/klix/engine.py` — `DecisionResult` hält Referenz auf Engine + `encoded`; `DecisionResult.explain(head_name)` delegiert
- Test: `tests/test_explain.py`

**Implementierung nearest-Pfad (der präzise Teil):**
- `Choice.evaluate` speichert pro evaluate nichts Extra; `explain()` rechnet aus vorhandenen Matrizen nach:
  1. Gewinner-Label + bester Anchor dieser Klasse (aus `category_scores`/`_label_rows`)
  2. Token-Beiträge: `q = self._sparse_query_vec(text)`; Anchor-Zeile aus `self.sparse_matrix[row]` → nicht-null Spalten schneiden mit q → Beitrag = q[col]·anchor[col]; Top-3 Tokens
  3. Dense-Similarity zum Anchor; Runner-Up
- Linear-Pfad: ehrlich Kennzeichnen `"kind": "probe"` — Sonde ist dense-only, daher keine Wort-Attribute; stattdessen dense-Similarity zum nächsten Anchor der Klasse + `reject_score`/Probability-Margin. Docstring sagt das explizit.
- `DecisionResult` bekommt `_engine` + `_encoded` (klein: 384 floats + sparse row); `explain(head)` ruft `head.explain(self._encoded, self.details(head))`

### Task 5.1: Choice.explain nearest-Pfad (TDD: assert Struktur + token "plc-34" taucht auf)
### Task 5.2: probe-Pfad + Score/Flag.explain
### Task 5.3: DecisionResult.explain + Demo-Abschnitt in `examples/production_pattern.py`

## Feature 1: `validate_anchors()` — 0.5.0

**API:**

```python
report = engine.validate_anchors()
# [{"head": "route", "a": "billing", "b": "finance", "centroid_cos": 0.87,
#   "shared_terms": ["freigeben", "approve"],
#   "a_exclusive": ["rechnung", "gutschrift"], "b_exclusive": ["budget", "kst"],
#   "misplaced": [{"text": "approve invoice", "closer_to": "finance"}],
#   "severity": "warn"}]
print(engine.validate_anchors_report())  # formatiert
```

**Files:**
- Create: `src/klix/validate.py`
- Modify: `src/klix/engine.py` — Delegation
- Test: `tests/test_validate.py`

**Logik (rein lesend, mutiert NIEMALS Anchors):**
1. Pro Choice-Kopf, pro Labelpaar: Centroid-Cosine (Mittel-Embedding je Klasse), minimaler Ankerpaar-Abstand
2. Shared terms: Tokens, die in beiden Klassen vorkommen (TF-IDF-Gewicht > x) — das sind die Verwechsler
3. Exclusive terms je Seite = Vorschläge zum Schärfen ("schärfe A mit: rechnung, gutschrift")
4. Misplaced anchors: Anchor, dessen Similarity zum Fremd-Centroid > 0.95 × Own-Centroid
5. Struktur-Warnungen: Klasse mit nur 1 Anchor, exakt doppelte Anchors, leere Klassen
6. Severity: `centroid_cos > 0.85` → "high", > 0.75 → "medium"

## Risiken / Tradeoffs / offene Fragen

1. **explain() im probe-Pfad** ist nicht token-exakt (Sonde sieht nur Dense) — Lösung: ehrliche Kennzeichnung, Sparse-Channel zusätzlich ausweisen. Nicht verschleiern.
2. **calibrate mit wenigen Samples** ist statistisch wackelig → Report enthält `n` + Warnung; Methode heißt explizit calibrate, nicht "optimize".
3. **Rules können Semantik killen** (force zu grob) → `matched_rules` immer in details, damit Debugging möglich ist; Docstring warnt.
4. **validate_anchors-Vorschläge** sind Heuristik — nie auto-anwenden, nur reporten (Design-Prinzip "honest signals").
5. **Batch + Streaming (echte C-Threads/Rust)** bewusst nach 0.5.x verschoben; ONNX intra-op-Parallelität dokumentieren statt Eigenbau-Threading.
6. Offen: impliziter Reject-Pol als Default (aus der Kaffeemaschinen-Diskussion) — Kandidat für 0.5.1, hier bewusst NICHT eingeplant (YAGNI bis Nutzer-Feedback vorliegt).
